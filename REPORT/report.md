# Мини-претрейн Qwen3: результаты и аудит

Проверена версия `913e4454a72bbc28182a60df637ef70b03060a7d` (minor fixes, 4 октября 2026). REPORT — папка; результаты уже сохранены в `output_dir/*/trainer_state.json` и `results/generations.txt`. Ниже анализ существующих запусков; новое обучение не проводилось.

## Конфигурация

Русская Wikipedia: `wikimedia/wikipedia`, `20231101.ru`; tokenizer `ai-forever/rugpt3small_based_on_gpt2`. Каждый документ обрезается до 512 токенов и дополняется справа до 512; pad = EOS. Данные записываются в 32 Parquet-шарда. Первые 5000 объектов загруженного датасета используются для validation, остальные для train, без предварительного перемешивания.

Qwen3ForCausalLM инициализируется с нуля: 12 слоёв, hidden size 2048, intermediate size 8192, 16 attention heads / 8 KV heads, head_dim 128. Используются FlashAttention 2, bfloat16 и TF32. Baseline: AdamW fused, LR 5e-5, weight decay 0.01, batch size 4 на устройство, accumulation 1, warmup 200 шагов, одна запланированная эпоха; логирование каждый шаг, validation каждые 100 шагов. Dockerfile фиксирует PyTorch 2.6.0, Transformers 4.52.0, datasets 3.6.0, flash-attn 2.7.3. A100 80 GB указана в предыдущем отчёте, но trainer_state не подтверждает модель GPU.

**Текущий your_solution.py имеет лимит 120 секунд. Экспериментальные скрипты имеют лимит 900 секунд. Сохранённые результаты нельзя выдавать за запуск текущего двухминутного скрипта.**

Baseline: train loss на первом шаге 11.1879; validation loss снижается с 10.35443 на шаге 100 до 8.49379 на шаге 200 и 7.50281 на шаге 1557. Последний batch loss 7.1755, средний train_loss за запуск 8.51765. Это разные величины: один batch, среднее по истории обучения и оценка финальных весов на validation. Baseline прошёл 0.003210 эпохи, то есть около 0.321% train.

![Baseline train и validation loss](images/baseline_loss.png)

График формируется из log_history: train — loss отдельных шагов, validation — периодические оценки. Числовая история подтверждает снижение loss; финальная validation-точка записана дважды на одном шаге и с одинаковым значением из-за двух вызовов evaluate. При построении стоит удалять такие дубликаты. По этим данным нельзя утверждать сходимость или отсутствие переобучения за пределами короткого запуска.

Частая validation расходует большую часть бюджета: в baseline оценки внутри trainer.train() суммарно занимают 752.15 из 950.49 секунд; затем отдельная финальная оценка занимает ещё 49.71 секунды. Таймер проверяется только после optimizer step, учитывает предыдущие оценки и может превысить лимит на длительность оценки. Эти запуски имеют 15-минутный лимит таймера, а не 15 минут чистой оптимизации. Для сравнения скорости нужно использовать фактические шаги / время и число полезных токенов; итоговые train_samples_per_second при досрочной остановке не следует принимать за измеренную пропускную способность.

## Генерации

Sampling: до 100 новых токенов, temperature 0.8, top_p 0.95. Сохранённая строка включает исходный prompt.

Примеры baseline (короткие фрагменты из results/generations.txt):

- «Москва — столица» → «Москва — столица, … Сингский район — — фамилия — деревня в городе.»
- «Искусственный интеллект — это» → «Искусственный интеллект — это в составе-Ском области, на территории-Бгу.»
- «В начале XX века Россия» → «В начале XX века Россия () — село, … В 1943 года, … История».

Модель воспроизводит заголовки и шаблоны Wikipedia, но продолжения не отвечают смыслу prompt, содержат искажённые слова, повторы и противоречия. Даже large_lr начинает с «Москва — столица собственное» и переключается на вымышленную деревню. У small_lr преобладают пустые строки и отдельные символы. Низкий loss здесь не доказывает осмысленность генераций. Large LR имеет лучший сохранённый eval loss среди пяти запусков, но одного запуска и трёх случайных генераций недостаточно для общего вывода об оптимальном LR или качестве модели.

## Ошибки и необходимые исправления

1. **Padding в labels — приоритетное исправление.** Сейчас labels копируются из input_ids без -100. Стандартный collator только собирает тензоры, а causal LM loss игнорирует -100, не attention_mask. Поэтому искусственные EOS/pad-цели участвуют в оптимизации и оценке. Это меняет задачу и может делать loss искусственно низким после освоения padding; величина и направление искажения конкретных результатов без данных и повторной оценки не установлены. Исправление:

   ```python
   tokens["labels"] = [
       [token_id if mask else -100 for token_id, mask in zip(ids, attention)]
       for ids, attention in zip(tokens["input_ids"], tokens["attention_mask"])
   ]
   ```

   Маскировать по attention_mask, а не по совпадению с pad_token_id: pad = EOS, поэтому иначе будут скрыты и настоящие EOS. Сдвиг labels вручную не нужен — модель делает его внутри loss. После изменения обязательно пересоздать Parquet или перемаскировать labels при загрузке: prepare_dataset пропускает подготовку, если найдены любые 32 Parquet-файла. Повторить обучение и оценку; старые числа сохранить как результаты ошибочного baseline. Измерить долю padding среди целевых позиций после causal shift.

2. **EOS и обрезание документов.** Код явно не добавляет настоящий EOS в конец текста; padding не заменяет эту границу. Для законченных документов добавить EOS с attention_mask=1, искусственные pads скрыть. Сохранить ограничение длины 512. Длинные статьи сейчас теряют весь хвост; разбиение на блоки или packing повысит использование корпуса, но изменит подготовку данных и требует отдельного сравнения.

3. **Время и лишняя оценка.** Сохранить предписанный лимит 120 секунд в основном решении. Уменьшить частоту промежуточных оценок, если условия задания позволяют; выполнить финальную оценку один раз. Для таймера использовать time.monotonic и отдельно учитывать оптимизацию, validation и полный runtime. Комментарий про best-checkpoint selection не соответствует load_best_model_at_end=False и save_strategy='no'.

4. **Воспроизводимость.** Seed нужно устанавливать до create_model: Trainer создаётся после случайной инициализации весов. Зафиксировать seed и для генераций, сохранить полную конфигурацию, версии и сведения о GPU. При сравнении batch учитывать разное число просмотренных примеров и полезных токенов; одинаковое время не изолирует эффект размера batch.

5. **Validation и артефакты.** Первые 5000 строк без shuffle не гарантируют репрезентативность. Если схема split не задана условиями, сделать фиксированный случайный split и проверку дубликатов. Проверять кеш по именам файлов и версии токенизации, а не только числу шардов. trainer.save_state сохраняет историю, но не веса; явно сохранить финальную модель и tokenizer, а eval_results — отдельным JSON. Без весов нельзя пересчитать исправленный loss для существующей модели или повторить её генерации.

Приоритет: маскирование labels и обновление кеша → повторный запуск с правильным лимитом → однократная финальная оценка и сохранение весов/метрик → обновление графиков и генераций. До этого результаты описывают освоение локальных шаблонов корпуса при некорректной обработке padding.

Проверка механики Transformers выполнена по исходникам версии 4.52.0: [causal LM loss](https://github.com/huggingface/transformers/blob/v4.52.0/src/transformers/loss/loss_utils.py), [default collator](https://github.com/huggingface/transformers/blob/v4.52.0/src/transformers/data/data_collator.py).
